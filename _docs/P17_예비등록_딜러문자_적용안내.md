# P17 예비등록 담당 딜러 문자 알림

상태: 코드·SQL만 준비됨. 이 문서는 배포 지시가 아니며 운영 DB, Edge Function, 네트워크에 적용하지 않았다.

## 동작

- 가족 명함 QR 등록이 실제로 `pre_registrations`에 INSERT된 경우에만 웹훅이 `send-alert`를 호출한다.
- `pre_registrations.dealer_id`는 `submit_pre_registration`에서 명함 쿠폰의 `issued_by`로 저장된다. 함수는 이 ID와 일치하는 `profiles` 한 행의 전화번호만 조회한다.
- 고정 SMS: `[10년의약속] 가족 안심 등록이 들어왔습니다. 확인하세요.` 가족 이름·전화번호·관계·지역은 포함하지 않는다. UTF-8 77바이트다.
- `sms_alert_phones`와 관리자 프로필은 이 분기에서 참조하지 않는다. 딜러 전화번호가 없으면 성공 응답으로 조용히 건너뛴다.
- `sms_alert_prereg_dealer`는 기본 `true`이고, 키가 아직 없어도 함수는 켜짐으로 본다. `false`일 때만 끈다.
- `sms_alert_prereg_hourly_cap`은 P17이 기본 `10`으로 추가한다. 같은 `dealer_id`의 최근 한 시간 INSERT 수가 상한을 넘으면 SMS만 생략한다(앱 내 등록 알림은 `submit_pre_registration`의 기존 처리 유지). 코드에는 숨은 숫자 기본값을 두지 않았다.

## 웹훅·인증 기준선

저장소와 Git 이력에는 `funeral-case-alert`/`profile-signup-alert`의 실제 운영 정의가 없었다. 운영 DB를 읽지 않는 범위에서는 URL·Authorization 값을 확인하거나 복제할 수 없다.

P17은 그 값을 추정하거나 소스에 비밀값을 쓰지 않는다. 실행 시 현재 `funeral-case-alert`의 `pg_get_triggerdef`에서 `supabase_functions.http_request(...)` 인자 전체(URL, Authorization 헤더, params, timeout)를 읽어 새 `pre-registration-dealer-alert` AFTER INSERT 트리거에 그대로 복제한다. 기준선이 없거나 같은 함수를 사용하지 않으면 실패하며 새 트리거를 만들지 않는다.

`supabase_functions.http_request`는 `net.http_post`로 비동기 요청을 큐에 넣는 기존 구조다. 따라서 Edge Function/NCP SMS 실패는 `submit_pre_registration` 트랜잭션을 되돌리지 않는다. INSERT가 없는 멱등 `exists` 반환 및 1시간 3회 제한 거절에는 새 웹훅도 생기지 않는다.

## 적용 및 되돌리기

1. `supabase functions deploy send-alert`
2. `_sql_admin_dealer/P17_예비등록_딜러문자.sql` 실행
3. 새 트리거가 활성화(`O`)인지, 기존 두 트리거 정의가 불변인지 읽기 전용 점검

되돌리기:

```sql
DROP TRIGGER IF EXISTS "pre-registration-dealer-alert" ON public.pre_registrations;
DELETE FROM public.system_config
WHERE key IN ('sms_alert_prereg_dealer','sms_alert_prereg_hourly_cap');
```

함수만 되돌릴 때는 이전 `send-alert` 소스를 재배포한다. 실제 운영 실행·배포는 이 변경에 포함되지 않는다.

## 상한 의견

딜러당 시간당 상한은 필요하다. 익명 가족 등록은 번호별 3회 제한만으로 서로 다른 번호를 통한 도배를 막지 못한다. 시작값 10은 정상 등록을 크게 방해하지 않으면서 급증을 억제하는 보수적 값이다. 상한 초과 건도 DB/앱 알림은 남기므로, 실제 운영량을 본 뒤 설정값만 조정하면 된다.
