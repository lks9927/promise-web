# 추가 매출 상태별 허용표 및 정산 상태 흐름

## 1. 정산 상태(settlements.status) 및 흐름 조사 결과

### 1.1 시스템 내 정산 상태값 조사
코드베이스 전수 조사 결과, `settlements.status`가 가질 수 있는 실제 값과 흐름은 다음과 같습니다:

1. **`draft` (정산예정)**
   - **위치/근거**: `src/components/admin/SettlementManager.jsx` 125~126줄(`ProgressPipeline`), 978~979줄.
   - **의미**: 장례 진행 중(`in_progress`) 또는 상담 완료 후 자동 생성된 정산 레코드의 초기 상태입니다.

2. **`awaiting_payment` (입금대기)**
   - **위치/근거**: `src/pages/TeamLeaderDashboard.jsx` 361~368줄, `src/components/admin/SettlementManager.jsx` 127~128줄, 980~991줄.
   - **의미**: 팀장이 장례를 종료(`team_settling` 전환)하면 모든 `draft` 정산 행이 `awaiting_payment`로 전환됩니다. 본사에 입금해야 할 금액(기본 사용료 + 추가 매출 수수료)이 입금되기를 기다리는 상태입니다.

3. **`pending` (지급대기 / 처리대기)**
   - **위치/근거**: `src/components/admin/SettlementManager.jsx` 129~130줄, 398~406줄, 992~1019줄.
   - **의미**: 본사 입금 확인이 완료되면 하위 출금 정산건(딜러 수수료, 마스터 오버라이드 등)이 `pending`(지급대기) 상태로 전환되어 본사 관리자의 '송금' 처리를 기다립니다.

4. **`paid` (입금/송금 완료)**
   - **위치/근거**: `src/components/admin/SettlementManager.jsx` 131~133줄, 391~396줄, 435~445줄.
   - **의미**: 본사 입금건(`usage_fee_remittance`, `extra_sales_fee`)의 입금이 확인되었거나, 하위 정산 대상자에게 송금이 완료된 상태입니다. 모든 정산이 `paid`가 되면 장례 사건이 `completed`로 전환됩니다.

5. **`completed` (완료)**
   - **위치/근거**: `src/components/admin/SettlementManager.jsx` 131~133줄, 495줄.
   - **의미**: 완료된 상태의 별칭 또는 레거시 완료 상태로 `paid`와 동등하게 완료로 취급됩니다.

### 1.2 '송금했음, 확인 대기' 상태값 존재 여부 보고
- **조사 결과**: 시스템에 **'팀장이 송금했음, 확인 대기'를 의미하는 별도의 `settlements.status` 값(예: `payment_submitted`, `remitted` 등)은 존재하지 않습니다.**
- **근거**:
  - `src/pages/TeamLeaderDashboard.jsx` 1381~1412줄: 팀장 화면에서 `team_settling` 단계 시 "장례 종료 및 본사 정산 입금 안내" 카드가 노출되며, 계좌 안내와 함께 "🟢 정산 확인 대기 (관리자 입금 확인 중)" 문구가 표시되지만 팀장이 누르는 '송금 완료 전송' 버튼이나 상태 변경 API 호출은 없습니다.
  - `src/components/team/MyWallet.jsx` 336~338줄: "본사 입금 확인 시 자동 정산 완료" 문구만 존재하며 별도의 송금 통보 기능이 없습니다.
  - `src/components/admin/SettlementManager.jsx` 380~422줄: 관리자가 계좌 입금을 확인한 후 `awaiting_payment` 상태의 입금 정산건(`usage_fee_remittance`, `extra_sales_fee`)에 대해 "입금확인" 버튼을 누르면 즉시 `paid`로 변경되고 케이스가 `hq_check`로 이동합니다.
- **결정 (지시서 지침 준수)**:
  - '송금했음, 확인 대기' 상태값이 시스템에 없으므로, 지시서에 따라 **`awaiting_payment`를 '갱신 가능'**, **`pending` 및 `paid`(또는 `completed`)를 '거부'** 로 확정합니다.

## 2. 상태별 추가 매출 등록·취소 허용표

## 3. 핵심 규칙 요약
1. **사건 상태 허용 조건**:
   - `funeral_cases.status IN ('in_progress', 'team_settling')` 일 때만 추가 매출 등록·취소(및 비공개 사진 첨부)가 허용됩니다.
   - `hq_check`, `completed`, `cancelled` 또는 기타 상태에서는 오류와 함께 즉시 차단됩니다: `"본사 입금 확인 이후에는 추가 매출을 수정할 수 없습니다."`
2. **정산 행 상태 제한 조건**:
   - 해당 사건의 정산 행 중 `status IN ('pending', 'paid', 'completed')` 인 행이 존재하면 거부됩니다: `"이미 입금 처리 중이라 수정할 수 없습니다."`
   - `draft` 및 `awaiting_payment` 상태는 갱신이 허용됩니다.
3. **수수료 행 갱신 및 상태 보존**:
   - 항목 등록/취소 시 수수료 행 `extra_sales_fee`는 ON CONFLICT DO UPDATE 시 기존 행의 `status`를 덮어쓰지 않고(`status = 'draft'` 강제 덮어쓰기 제거) 금액(`amount`, `base_amount`, `tax_amount`, `net_amount`)만 재계산하여 갱신합니다.
   - `team_settling` 상태에서 새로 수수료 행이 INSERT되는 경우 처음부터 `awaiting_payment` 상태로 생성됩니다.
4. **취소 제외 시 삭제**:
   - 유효한 추가 매출 총합이 0이 되면 `extra_sales_fee` 행은 자동으로 삭제됩니다.
