# P3 정산 초안 트리거와 정책 정산 함수의 충돌 점검

검토 기준은 2026-11-04 저장본이다. 아래는 **확인된 함수 본문**에 대한 정적 점검이며 운영 DB는 수정하거나 조회하지 않았다.

| 구분 | 확인된 사실 | 영향/어긋나는 시나리오 |
|---|---|---|
| 생성 시점 | `auto_create_draft_settlements`는 팀장 지정 사건의 INSERT/팀장 변경 뒤에 초안을 만든다. | 상담 시작 전부터 초안이 존재할 수 있다. |
| 하드코딩 초안 | 같은 함수는 `usage_fee_remittance` 750,000, `leader_override` 50,000, `dealer_commission` 200,000, `dealer_override` 50,000을 고정값으로 넣는다. | 정책 금액이나 세금 계산 방식과 달라질 수 있다. |
| 정책 정산 | `calculate_settlements`는 `in_progress` 전환 시 `commission_policies`를 읽고 같은 `usage_fee_remittance`, `dealer_commission`, `dealer_override`, `leader_override` type을 삽입한다. 쿠폰이면 `customer_cashback`도 삽입한다. | 앞의 네 type은 같은 사건·수령인·type 조합이 겹칠 수 있다. |
| P1a 상호작용 | P1a의 각 INSERT는 `unique_settlement_per_case`에 `ON CONFLICT DO NOTHING`을 사용한다. | 초안이 먼저 있으면 정책 정산 INSERT가 건너뛰어 고정값 초안이 그대로 남는다. `usage_fee_remittance`는 특히 750,000과 정책 `base_margin`이 다르면 어긋난다. `dealer_commission`은 고정 200,000/세금 방식과 정책 금액/3.3% 순액이 다를 수 있다. |

| 해결 선택지 | 장점 | 주의점 |
|---|---|---|
| 초안 트리거 제거 | 단일 정책 원천으로 즉시 일관성 확보 | 상담 시작 전 초안 표시 흐름이 사라진다. |
| 초안 트리거가 정책을 읽도록 수정 | 기존 초안 UX를 유지하면서 금액 일치 | INSERT와 in_progress 시점 중 어느 정책 스냅샷을 쓸지 명확히 해야 한다. |
| `ON CONFLICT DO UPDATE` | 시작 시점에 정책값으로 정정 가능 | 관리자 검토/확정한 초안까지 덮어쓸 위험이 있어 상태 조건이 필수다. |

**권장안:** 초안 흐름이 필요하다면 두 번째 선택지로 `auto_create_draft_settlements`가 같은 `commission_policies`와 세금 규칙을 읽게 하고, `calculate_settlements`는 이미 존재하는 `draft`만 정책값으로 안전하게 보정하도록 제한한다. 초안이 운영상 필요 없으면 트리거를 제거하는 편이 더 단순하다. 어떤 경우에도 확정·지급된 정산을 `DO UPDATE`로 덮어쓰면 안 된다.
